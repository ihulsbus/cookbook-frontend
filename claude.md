# CLAUDE.md — TypeScript Project Guidelines

## Code Quality Rules

1. **Readability first** - Code should be self-documenting. Use descriptive names, keep functions focused, and add comments only for non-obvious decisions.
2. **Single Responsibility** - Each function, class, and module should have one reason to change. If you cannot describe what a function does without "and", split it.
3. **Explicit error handling** - Handle errors at the point where you have enough context to do something useful. Never silently swallow errors.
4. **Immutability by default** - Use const/let over var, readonly properties, and immutable data structures where possible. Mutate only when performance requires it.
5. **Test critical paths** - Focus testing effort on business logic and edge cases, not trivial getters. Aim for 80% coverage on core modules.
6. **DRY but not prematurely** - Duplicate code twice before abstracting. Three occurrences justify a shared function; two might be coincidence.
7. **Keep dependencies lean** - Audit every new dependency. Prefer well-maintained packages with small surface area.
8. **Fail fast** - Validate inputs at function boundaries. Return early for invalid states. Do not let bad data propagate deep into the system.

## TypeScript Conventions

- Strict mode enabled (`"strict": true` in tsconfig.json)
- No `any` types - use `unknown` with type guards instead
- Prefer `interface` over `type` for object shapes
- Use `as const` for literal types
- Exhaustive switch with `never` type for union narrowing
- All function parameters and return types explicitly typed
- Use named exports, not default exports
- Prefer `const` over `let`; never use `var`

## Team Conventions (Solo Developer)

- Commit frequently with descriptive messages; future-you is your code reviewer
- Use branches for experiments; merge or delete within a week
- Write at least smoke tests for critical paths; skip unit tests for throwaway code
- Keep a DECISIONS.md log for architectural choices so you remember why later
- Automate deployment so you never forget a step

## Testing Rules

- Place tests as `*.test.ts` next to source files
- Use `describe`/`it` blocks for grouping; one assertion per `it` block preferred
- Mock external dependencies; never mock the module under test
- Use factory functions for test data, not shared mutable fixtures
- Run with coverage; enforce minimum 80% on critical modules
- Test edge cases: empty inputs, null values, error paths, boundary conditions

## Git Workflow

- Write commit messages in imperative mood: "Add feature" not "Added feature"
- Keep commits atomic: one logical change per commit
- Never commit generated files, build artifacts, or secrets
- Use `.gitignore` to exclude: `node_modules/`, `dist/`, `.env`, `*.log`, IDE configs
- Squash fixup commits before merging to main
- Never force-push to shared branches (main, develop)
- Tag releases with semantic versions: `v1.2.3`
- Write meaningful PR descriptions that explain the "why"

## Documentation Rules

- Every public function must have a doc comment explaining its purpose, parameters, and return value
- Keep a CHANGELOG.md updated with notable changes per version
- Write ADRs (Architecture Decision Records) for significant technical decisions
- README.md must include: project description, setup instructions, and contribution guidelines
- Inline comments explain "why", not "what" - the code should explain "what"
- API endpoints must be documented with request/response examples
- Update documentation in the same PR that changes the code

## Security Rules

- Never commit secrets, API keys, tokens, or passwords to version control
- Use environment variables or secret managers for all credentials
- Validate and sanitize all user input at system boundaries
- Use parameterized queries; never concatenate user input into SQL or commands
- Set Content Security Policy (CSP) headers on web applications
- Keep dependencies updated; run `npm audit` / `pip audit` / equivalent regularly
- Use HTTPS everywhere; never serve anything over plain HTTP in production
- Implement rate limiting on public API endpoints
- Log security-relevant events (auth failures, permission denials, input validation errors)
- Follow the principle of least privilege for all service accounts and IAM roles
